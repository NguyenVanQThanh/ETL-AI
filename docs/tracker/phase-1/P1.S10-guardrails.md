## 2. Công nghệ / Tech sử dụng

| Tech | Vai trò trong buổi này | Version/note |
|---|---|---|
| Postgres roles/privileges | Lớp bảo vệ chính — role `agent_readonly` chỉ `SELECT` trên schema `marts` | `GRANT USAGE ON SCHEMA` + `GRANT SELECT ON ALL TABLES IN SCHEMA` |
| psycopg (psycopg2/psycopg3) | Kết nối DB, set `statement_timeout` ở connection option | `options='-c statement_timeout=5000'` hoặc `SET LOCAL` trong transaction |
| Python (regex/`sqlparse` tuỳ chọn) | Lớp chặn sớm phụ — fail-fast trước khi gửi SQL xuống DB | regex đơn giản đủ cho buổi này, không bắt buộc AST parser |

## 3. Kiến thức quan trọng / Keyword cần nắm

- **Least privilege / read-only role** — tạo role Postgres chỉ có `CONNECT` + `USAGE` trên schema + `SELECT` trên table, không có `INSERT/UPDATE/DELETE/CREATE/DROP`. Đây là **lớp bảo vệ CHÍNH** của toàn bộ guardrail: dù LLM sinh SQL phá hoại (`DROP TABLE`, `DELETE FROM ...`), DB tự trả `permission denied` — không phụ thuộc code Python có bug hay không.
- **`statement_timeout`** — giới hạn thời gian 1 câu query được chạy trước khi Postgres tự kill. Set ở connection (`options='-c statement_timeout=5000'`) hoặc per-transaction (`SET LOCAL statement_timeout = '5s'`). Chặn agent vô tình sinh query full table scan/join chéo làm treo DB.
- **LIMIT injection tự động** — nếu SQL agent sinh ra không có `LIMIT`, code Python tự thêm `LIMIT 100` trước khi execute. Tránh trả về triệu row làm crash agent/UI, không liên quan tới an toàn ghi/xoá data nhưng vẫn là 1 lớp bảo vệ tài nguyên.
- **Defense-in-depth (nhiều lớp, không tin 1 lớp duy nhất)** — thứ tự lớp từ mạnh → yếu:
  1. **DB role permission** (mạnh nhất, enforce ở tầng DB, không thể bypass từ code)
  2. **statement_timeout** (chặn resource abuse, không chặn được DML hợp lệ nhưng chạy lâu)
  3. **LIMIT tự thêm** (chặn resource abuse ở tầng result set)
  4. **Regex/keyword blocking DML/DDL** (yếu nhất — chỉ là fail-fast ở tầng ứng dụng)
- **Vì sao regex-only không đủ** — regex substring-match dễ bị bypass bằng comment injection (`/* DROP */ TABLE`), homoglyph Unicode, hoặc câu hợp lệ về cú pháp nhưng phá hoại dữ liệu (`DELETE FROM orders` không có `WHERE` — không chứa keyword "nguy hiểm" nào ngoài `DELETE`). Regex cũng false-positive với từ tiếng Anh thông thường chứa substring keyword. Regex chỉ nên là lớp chặn sớm cho UX (báo lỗi nhanh, không tốn round-trip DB) — **không phải lớp an toàn thật**, lớp an toàn thật là DB role.

## 4. Các bước nhỏ (step-by-step)

1. **Tạo Postgres role `agent_readonly` chỉ SELECT trên schema `marts`**
   - Dùng superuser tạm thời chạy:
     ```sql
     CREATE ROLE agent_readonly LOGIN PASSWORD '<đặt trong .env, không hardcode>';
     GRANT CONNECT ON DATABASE <dbname> TO agent_readonly;
     GRANT USAGE ON SCHEMA marts TO agent_readonly;
     GRANT SELECT ON ALL TABLES IN SCHEMA marts TO agent_readonly;
     ALTER DEFAULT PRIVILEGES IN SCHEMA marts GRANT SELECT ON TABLES TO agent_readonly;
     ```
   - Kỳ vọng: role không có `CREATE`, không có quyền gì trên schema khác ngoài `marts`.
   - ⚠️ Lỗi thường gặp: quên `GRANT USAGE ON SCHEMA` → `GRANT SELECT` không lỗi lúc chạy nhưng agent connect vào sẽ bị `permission denied for schema` khi query — thiếu USAGE là nguyên nhân số 1.
2. **Đổi connection string agent dùng sang role `agent_readonly`**
   - Sửa `.env`/config agent (biến kiểu `AGENT_DB_USER`, `AGENT_DB_PASSWORD`) → không còn dùng credential superuser/owner.
   - Kỳ vọng: agent connect được, query `SELECT` trên `marts` chạy bình thường.
3. **Set `statement_timeout` ở connection**
   - psycopg: `psycopg2.connect(..., options='-c statement_timeout=5000')` (5000ms = 5s) — hoặc `SET LOCAL statement_timeout = '5s'` đầu mỗi transaction nếu dùng connection pool.
   - Kỳ vọng: thử query giả lập chậm (`pg_sleep(10)`) → bị kill sau ~5s với lỗi `canceling statement due to statement timeout`.
4. **Viết hàm tự thêm `LIMIT 100` nếu SQL sinh ra thiếu**
   - Parse chuỗi SQL (case-insensitive), check có `LIMIT` chưa (regex đơn giản đủ, không cần parser đầy đủ cho việc này vì chỉ là bổ sung, không phải chặn bảo mật).
   - Có → giữ nguyên. Không có → append `LIMIT 100` trước khi execute.
   - Kỳ vọng: SQL agent sinh không LIMIT vẫn trả về tối đa 100 row.
5. **Viết regex/parse chặn keyword DML/DDL — lớp chặn sớm bổ sung**
   - Regex match (word-boundary, case-insensitive) các keyword: `INSERT|UPDATE|DELETE|ALTER|DROP|CREATE|TRUNCATE|GRANT|REVOKE`.
   - Match → reject ngay tại code Python, KHÔNG gửi xuống DB, trả lỗi rõ cho user.
   - **Ghi rõ trong code comment**: đây chỉ là lớp phụ fail-fast, lớp an toàn thật là DB role (bước 1). Không tự tin regex chặn được hết — biết trước có thể bypass bằng comment injection hoặc câu cú pháp hợp lệ khác không chứa keyword nào.
6. **Test cố tình cho agent sinh SQL phá hoại — verify chặn ở tầng role**
   - Hỏi agent các câu ép sinh SQL nguy hiểm: "xoá hết data trong bảng orders", "update giá tất cả sản phẩm thành 0", "drop table customers".
   - Kỳ vọng: nếu regex bắt được → reject sớm (log lại). Nếu cố tình bypass regex (test riêng bằng cách gọi thẳng hàm execute với câu DML/DDL, bỏ qua lớp regex) → DB phải trả `permission denied for table/schema` — đây là bằng chứng lớp role hoạt động độc lập, không phụ thuộc regex.
   - ⚠️ Lỗi thường gặp: nếu test chỉ đi qua đường agent (luôn bị regex chặn trước) thì KHÔNG verify được lớp role có hoạt động thật hay không — phải có test bypass thẳng lớp regex để chắc chắn role là lớp chặn cuối.

## 5. Output mong muốn

- [ ] Role `agent_readonly` tồn tại trong Postgres, verify bằng `psql -c "\du agent_readonly"` và thử `INSERT`/`DROP` trực tiếp bằng role này → nhận `permission denied`
- [ ] Agent dùng connection string với `agent_readonly`, `statement_timeout` set ở connection (verify bằng `SHOW statement_timeout;` trong session agent hoặc test `pg_sleep`)
- [ ] Hàm tự thêm `LIMIT 100` có unit test: 1 case input thiếu LIMIT → output có `LIMIT 100`; 1 case input đã có LIMIT → giữ nguyên
- [ ] Regex chặn DML/DDL có unit test: ≥1 case match (reject) + ≥1 case SQL SELECT hợp lệ không bị chặn nhầm (false positive)
- [ ] Chạy thử ≥3 câu hỏi "độc hại" qua agent thật (xoá/sửa/drop) → agent không phá được data, log lại lớp nào đã chặn (regex hay DB role) cho mỗi câu
- [ ] File/artifact cụ thể: script tạo role (`.sql` hoặc ghi trong migration), hàm guardrail Python (LIMIT + regex), test file tương ứng — path cụ thể tuỳ cấu trúc repo hiện có
- [ ] Cách tự kiểm tra: chạy test suite guardrail (`pytest` case LIMIT + regex) PASS 100%, chạy thử tay 3 câu hỏi độc hại và xác nhận log chặn đúng tầng
