## 2. Công nghệ / Tech sử dụng

| Tech | Vai trò trong buổi này | Version/note |
|---|---|---|
| dbt-core generic tests | Test tự động khóa chính/khóa ngoại trên mart models | `unique`, `not_null`, `relationships`, `accepted_values` — 4 test built-in |

## 3. Kiến thức quan trọng / Keyword cần nắm

Danh sách khái niệm PHẢI hiểu được (không chỉ copy-paste code) trước khi coi buổi này là xong:

- **Generic tests (`unique`, `not_null`, `relationships`, `accepted_values`)** — test tham số hóa, khai báo trong `schema.yml` dưới cột/model, không cần viết SQL. `unique`/`not_null` áp cho khóa chính; `relationships` kiểm khóa ngoại tồn tại ở bảng cha (referential integrity).
- **Singular test** — test SQL tự viết, đặt file `.sql` trong `tests/`, PASS khi query trả 0 row. Dùng cho rule nghiệp vụ generic test không cover được (vd: `order_total` không được âm).
- **Test severity (`error` vs `warn`)** — config `severity: warn` cho phép test fail mà không làm `dbt test` exit code lỗi (dùng khi biết data có edge case chấp nhận được, chưa muốn block CI). Mặc định là `error`.
- **`manifest.json`** — metadata toàn bộ DAG (models, tests, sources, dependencies, compiled SQL). Sinh ra ở mọi lệnh dbt (`run`, `test`, `compile`...), không chỉ `docs generate`.
- **`catalog.json`** — metadata cột/bảng THẬT lấy từ warehouse (data type, có tồn tại không) — chỉ sinh khi chạy `dbt docs generate`, khác `manifest.json` (metadata khai báo trong code).

## 4. Các bước nhỏ (step-by-step)

1. **Viết `schema.yml` cho mỗi mart model — khai báo `data_tests`**
   - Trong `models/marts/schema.yml` (hoặc file riêng mỗi model), với mỗi fact/dim table khai báo cột khóa chính:
     ```yaml
     models:
       - name: dim_customer
         columns:
           - name: customer_id
             data_tests:
               - unique
               - not_null
     ```
   - Kỳ vọng: mọi mart model (4 dim + 1 fact) đều có ít nhất `unique` + `not_null` trên PK.
   - ⚠️ Lỗi thường gặp: dùng key `tests:` cũ vẫn chạy được (dbt >=1.8 chỉ deprecate, chưa xóa) — không phải lỗi hard-fail, nhưng nên dùng `data_tests:` cho đồng bộ về sau.

2. **Khai báo `relationships` cho khóa ngoại của `fact_orders`**
   - Mỗi FK trong `fact_orders` (vd `customer_id`, `product_id`) test `relationships` trỏ về dim tương ứng:
     ```yaml
     - name: customer_id
       data_tests:
         - relationships:
             to: ref('dim_customer')
             field: customer_id
     ```
   - Kỳ vọng: mọi FK trong `fact_orders` có test `relationships`, không còn orphan record (row fact trỏ tới dim không tồn tại).

3. **Chạy `dbt test`, fix data quality issue nếu fail**
   - `dbt test` — chạy toàn bộ generic tests vừa khai báo.
   - Fail → đọc log biết đúng model/column nào fail, kiểm tra data gốc (duplicate key, NULL không mong đợi, FK orphan) → fix ở model SQL (staging/marts) hoặc source, KHÔNG sửa test để né fail.
   - ⚠️ Lỗi thường gặp: fail vì data thật có edge case chấp nhận được (vd vài row NULL hợp lệ) → cân nhắc `severity: warn` thay vì xóa test, nhưng phải ghi rõ lý do trong comment schema.yml.

4. **`dbt docs generate`**
   - Sinh `target/manifest.json` (update) + `target/catalog.json` (mới, chứa metadata cột/bảng thật từ warehouse).
   - Kỳ vọng: lệnh chạy xong không lỗi, 2 file tồn tại trong `target/`.

5. **`dbt docs serve` — xem thử UI lineage**
   - Mở server local (mặc định port 8080), xem lineage graph (DAG staging → marts), click vào model xem description/columns đã khai báo.
   - Đây là bước xem thử để verify docs render đúng — KHÔNG dùng `docs serve` cho production (chỉ dev convenience).

> Step nào có rủi ro/lỗi thường gặp đã ghi chú "⚠️ Lỗi thường gặp" ngay dưới step đó.

## 5. Output mong muốn

- [ ] `dbt test` chạy PASS 100% (0 fail, 0 error) trên toàn bộ mart models
- [ ] `target/manifest.json` tồn tại và đã update sau lần chạy gần nhất
- [ ] `target/catalog.json` tồn tại (sinh từ `dbt docs generate`)
- [ ] Verify bằng lệnh:
  ```bash
  dbt test
  ls target/manifest.json target/catalog.json
  ```
