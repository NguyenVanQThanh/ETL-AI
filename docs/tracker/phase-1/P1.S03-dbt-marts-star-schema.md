## 3. Kiến thức quan trọng / Keyword cần nắm

Danh sách khái niệm PHẢI hiểu được (không chỉ copy-paste code) trước khi coi buổi này là xong:

- **Fact table vs dimension table** — fact table chứa số đo (measure) + foreign key trỏ tới các dimension (vd `fact_orders` chứa `quantity`, `amount`, `customer_key`, `product_key`...); dimension table chứa thuộc tính mô tả (vd `dim_customer` chứa tên, địa chỉ, segment). Fact table thường nhiều row, ít cột; dimension table ít row hơn, nhiều cột mô tả.
- **Grain (độ chi tiết của fact table)** — định nghĩa rõ "1 row trong fact_orders đại diện cho cái gì". Buổi này chọn grain = **1 row = 1 order_item** (1 dòng sản phẩm trong 1 order), không phải 1 row = 1 order — vì order thường có nhiều sản phẩm, cần giữ chi tiết đến mức item để phân tích theo product/quantity/amount từng dòng. Chọn sai grain (quá thô hoặc quá chi tiết) là lỗi thiết kế star schema phổ biến nhất.
- **Surrogate key vs natural key** — natural key là ID có sẵn từ source (vd `customer_id`, `order_id`); surrogate key là key sinh riêng trong warehouse (thường hash từ 1 hoặc nhiều cột), dùng làm primary key/foreign key trong star schema thay vì dùng trực tiếp natural key. Lý do dùng surrogate key: cách ly warehouse khỏi thay đổi ở source (đổi kiểu ID, trùng ID giữa nhiều source), và là điều kiện cần để làm SCD Type 2 sau này (P1.S14).
- **SCD Type 1 (overwrite, không giữ lịch sử)** — khi dimension row thay đổi (vd customer đổi địa chỉ), SCD Type 1 ghi đè giá trị cũ, không giữ lại bản cũ. Đơn giản, phù hợp buổi này. SCD Type 2 (giữ lịch sử qua `valid_from`/`valid_to` hoặc versioning) làm ở P1.S14, KHÔNG làm ở đây.
- **Date dimension (`dim_date`)** — dimension đặc biệt không lấy từ bảng source nào, mà tự sinh ra 1 dãy ngày liên tục (date spine) rồi thêm các cột phái sinh (year, month, quarter, day_of_week...). Dùng `dbt_utils.date_spine` để sinh chuỗi ngày này.

## 4. Các bước nhỏ (step-by-step)

1. **Thêm package `dbt_utils` vào `packages.yml`**
   - Tạo/sửa file `packages.yml` ở root project dbt:
     ```yaml
     packages:
       - package: dbt-labs/dbt_utils
         version: [">=1.1.0", "<2.0.0"]
     ```
   - Chạy `dbt deps` để install.
   - Kỳ vọng: thấy folder `dbt_packages/dbt_utils` xuất hiện, không có lỗi version conflict.

2. **Xây `dim_customer`, `dim_product`, `dim_seller` từ staging**
   - Mỗi dimension: `SELECT` từ `{{ ref('stg_customers') }}` (tương tự cho product, seller), dedupe theo natural key (`customer_id`...) bằng `distinct` hoặc `qualify row_number()` nếu source có duplicate.
   - Sinh surrogate key bằng `dbt_utils.generate_surrogate_key(['customer_id'])` (natural key làm input) → cột `customer_key`.
   - Áp dụng SCD Type 1: không cần logic đặc biệt — cứ `dbt run` lại, giá trị mới tự ghi đè giá trị cũ (vì materialization là `table`, rebuild toàn bộ mỗi lần chạy — chưa cần incremental ở buổi này).
   - Khai báo `materialized='table'` cho marts (khác staging thường để `view`) — vì marts là layer để BI/analyst query trực tiếp, cần tốc độ đọc nhanh, không cần build lại mỗi lần query như view.
   - Kỳ vọng: mỗi dim model có 1 cột `*_key` (surrogate) + giữ nguyên natural key gốc để trace ngược, không duplicate row theo natural key.
   - ⚠️ Lỗi thường gặp: quên dedupe → dimension có nhiều row cùng natural key → khi join với fact sẽ bị fan-out (nhân đôi số liệu).

3. **Xây `dim_date` bằng date spine**
   - Dùng `dbt_utils.date_spine(datepart="day", start_date="cast('2018-01-01' as date)", end_date="cast('2025-12-31' as date)")` (chọn range phù hợp dữ liệu order thực tế).
   - Thêm các cột phái sinh: `year`, `quarter`, `month`, `day_of_week`, `is_weekend`... bằng hàm date của DB.
   - Surrogate key `date_key` có thể chính là `date_day` format số (vd `20250115`) — không cần hash vì đã là key tự nhiên duy nhất.
   - Kỳ vọng: `dim_date` có đủ 1 row/ngày, không gap, cột derived đúng.

4. **Xây `fact_orders` — join staging orders + order_items, xác định rõ grain**
   - Grain: **1 row = 1 order_item** (đã chốt ở mục 3).
   - Join `{{ ref('stg_order_items') }}` với `{{ ref('stg_orders') }}` (lấy thông tin order-level như order_date, customer_id) → join tiếp `dim_customer`, `dim_product`, `dim_seller`, `dim_date` để lấy surrogate key tương ứng (join theo natural key, output ra `*_key`).
   - Cột measure: `quantity`, `unit_price`, `amount` (hoặc tương đương theo schema thực tế của source data).
   - Foreign key: `customer_key`, `product_key`, `seller_key`, `date_key`.
   - Kỳ vọng: mỗi row `fact_orders` map đúng 1 order_item, đủ FK trỏ tới 4 dimension, không mất row so với `stg_order_items` (check bằng đếm count).
   - ⚠️ Lỗi thường gặp: join sai điều kiện làm mất row hoặc nhân đôi row (fan-out) — luôn so sánh `count(*)` fact vs staging trước/sau join.

5. **`dbt run` toàn bộ marts**
   - Chạy `dbt run --select marts` (hoặc tag tương ứng nếu đã đặt tag).
   - Kỳ vọng: 5 model (`dim_customer`, `dim_product`, `dim_seller`, `dim_date`, `fact_orders`) build thành công, nằm trong schema `marts`.

- [ ] File model tạo ra tại: `models/marts/dim_customer.sql`, `models/marts/dim_product.sql`, `models/marts/dim_seller.sql`, `models/marts/dim_date.sql`, `models/marts/fact_orders.sql` (đường dẫn cụ thể theo cấu trúc project thực tế)
- [ ] Query thử join `fact_orders` với `dim_customer` ra kết quả đúng, vd:
  ```sql
  select c.customer_id, count(*) as n_order_items, sum(f.amount) as total_amount
  from marts.fact_orders f
  join marts.dim_customer c on f.customer_key = c.customer_key
  group by 1
  order by 2 desc
  limit 10;
  ```
  — trả về kết quả có ý nghĩa (không toàn NULL, không 0 row)
