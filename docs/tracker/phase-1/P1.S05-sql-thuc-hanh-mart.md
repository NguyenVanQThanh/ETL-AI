## 3. Kiến thức quan trọng / Keyword cần nắm

Danh sách khái niệm PHẢI hiểu được (không chỉ copy-paste code) trước khi coi buổi này là xong:

- **Window function (`OVER`, `PARTITION BY`)** — tính toán trên một "cửa sổ" các row liên quan mà KHÔNG collapse row như `GROUP BY`. `PARTITION BY` chia dữ liệu thành nhóm (vd theo seller), `ORDER BY` trong `OVER` quyết định thứ tự tính (rank, running total...).
- **ROW_NUMBER vs RANK vs DENSE_RANK** — cả 3 đều gán số thứ tự theo `ORDER BY`, khác nhau khi có giá trị trùng: `ROW_NUMBER` luôn tăng dần không trùng (1,2,3,4); `RANK` giữ trùng số cho giá trị bằng nhau nhưng nhảy số sau đó (1,2,2,4); `DENSE_RANK` giữ trùng số và KHÔNG nhảy số (1,2,2,3).
- **LAG / LEAD** — lấy giá trị của row trước (`LAG`) hoặc sau (`LEAD`) trong cùng partition, dùng cho so sánh kỳ-này-với-kỳ-trước (tăng/giảm doanh thu, khoảng cách giữa 2 đơn hàng liên tiếp) mà không cần self-join.
- **CTE (`WITH` clause)** — đặt tên cho một subquery để tái dùng/đọc dễ hơn trong query chính; non-recursive CTE chỉ là "subquery có tên", recursive CTE (`WITH RECURSIVE`) dùng cho dữ liệu có cấu trúc lặp/cây (ít gặp trên mart e-commerce dạng bảng phẳng, nhưng cần biết khác biệt).
- **EXISTS vs IN vs JOIN** — `EXISTS` dừng ngay khi tìm thấy 1 row khớp (tốt cho check tồn tại), `IN` build full list rồi so sánh (chậm hơn với subquery lớn hoặc có `NULL`), `JOIN` dùng khi cần lấy thêm cột từ bảng kia — chọn theo mục đích (chỉ check tồn tại → `EXISTS`; cần dữ liệu → `JOIN`).
- **Query plan (Seq Scan, Index Scan, cost, rows, actual time)** — `EXPLAIN ANALYZE` chạy query THẬT và trả về plan cây: mỗi node ghi loại scan, `cost=ước tính..ước tính` (đơn vị tương đối, không phải giây), `rows=` số row Postgres ước tính node đó trả về, và khi chạy `ANALYZE` còn có `actual time=first_row..last_row` (ms thật) + `rows=` thật. Seq Scan đọc toàn bộ bảng tuần tự; Index Scan dùng index để nhảy thẳng đến row cần. Chênh lệch lớn giữa `rows` ước tính và actual → statistics bị stale, nên chạy lại `ANALYZE table_name;`.
- **Khi nào thêm index, khi nào không cần** — B-tree index tối ưu cho point lookup (tìm 1-vài row theo điều kiện chọn lọc), KHÔNG tối ưu cho aggregation quét rộng kiểu OLAP. Với dataset nhỏ (mart Olist ở scale học tập), Postgres planner thường CHỌN ĐÚNG Seq Scan vì đọc tuần tự rẻ hơn random seek qua index — thêm index không giúp, đôi khi query plan không đổi. Nguyên tắc: viết query trước không index, đo bằng `EXPLAIN ANALYZE`, chỉ thêm index khi đo thấy cải thiện rõ trên cột lọc/join chọn lọc cao; đừng thêm "phòng khi".

## 4. Các bước nhỏ (step-by-step)

1. **Lên ý tưởng 10 query trên schema marts Olist**
   - Danh sách cụ thể (mỗi ý = 1 file sau này):
     1. `01_top_sellers_by_revenue_monthly.sql` — top 5 seller theo revenue mỗi tháng, dùng `ROW_NUMBER() OVER (PARTITION BY month ORDER BY revenue DESC)`, lọc `WHERE row_num <= 5` qua CTE.
     2. `02_order_value_vs_previous_order.sql` — so sánh order value hiện tại với order NGAY TRƯỚC của cùng customer, dùng `LAG(order_value) OVER (PARTITION BY customer_id ORDER BY order_date)`.
     3. `03_days_between_orders.sql` — khoảng cách ngày giữa 2 order liên tiếp của cùng customer (gap analysis), dùng `LAG(order_date)` rồi trừ ngày.
     4. `04_next_order_prediction_window.sql` — dùng `LEAD(order_date)` xem đơn tiếp theo (nếu có) của customer, phục vụ phân tích churn/retention.
     5. `05_seller_rank_dense_vs_row_number.sql` — 1 query so sánh trực tiếp `ROW_NUMBER`, `RANK`, `DENSE_RANK` cùng lúc trên revenue seller để thấy khác biệt khi có giá trị trùng.
     6. `06_customer_retention_cte.sql` — CTE tính retention: CTE 1 lấy tháng-order-đầu-tiên mỗi customer, CTE 2 join lại đếm số customer còn active tháng kế tiếp.
     7. `07_running_total_revenue.sql` — running total revenue theo thời gian dùng `SUM(revenue) OVER (ORDER BY month)`.
     8. `08_customers_with_no_review_exists.sql` — dùng `NOT EXISTS` tìm order KHÔNG có review, so với cách viết `NOT IN` để đối chiếu.
     9. `09_sellers_with_late_delivery_exists.sql` — dùng `EXISTS` + `JOIN` kết hợp tìm seller có ít nhất 1 đơn giao trễ, kèm CTE tổng hợp tỉ lệ trễ.
     10. `10_category_revenue_share_cte.sql` — CTE tính tổng revenue toàn shop, query chính tính % revenue mỗi category so với tổng (window function `SUM() OVER ()` không partition).
   - Kỳ vọng: có list 10 ý tưởng rõ ràng, map được tới cột/bảng thật trong schema marts trước khi viết SQL.
2. **Viết từng file `.sql` trong `sql/analysis/`**
   - Mỗi file: 1 query hoàn chỉnh, có comment đầu file nêu mục đích + keyword chính dùng (vd `-- Window function: LAG, dùng để so sánh order value với order trước`).
   - Chạy thử từng file trên DB thật, xác nhận không lỗi cú pháp và ra kết quả hợp lý (số dòng > 0, giá trị không âm bất thường).
   - ⚠️ Lỗi thường gặp: quên `PARTITION BY` → `LAG`/`ROW_NUMBER` tính xuyên toàn bảng thay vì theo nhóm, ra kết quả sai âm thầm (không báo lỗi).
3. **Chọn 2-3 query nặng nhất, chạy `EXPLAIN ANALYZE`**
   - Ưu tiên query có nhiều JOIN + window function trên nhiều row (vd query #6, #9, #10 — có CTE + join + aggregate).
   - Chạy `EXPLAIN ANALYZE <query>`, đọc: loại scan (Seq Scan/Index Scan), `cost`, `rows` ước tính vs `rows` actual, `actual time`.
   - Ghi lại kết quả plan TRƯỚC khi đổi gì (copy phần quan trọng vào file hoặc note riêng).
4. **Thử thêm index, so sánh lại**
   - Với cột dùng để `JOIN`/`WHERE`/`PARTITION BY` chọn lọc cao trong query chậm nhất, thử `CREATE INDEX idx_<table>_<col> ON <table>(<col>);`.
   - Chạy lại `EXPLAIN ANALYZE` cùng query, so sánh `cost`/`actual time` trước-sau.
   - Kỳ vọng thấy 1 trong 2 kết quả: (a) plan đổi sang Index Scan, thời gian giảm rõ — ghi lại làm minh chứng; (b) plan KHÔNG đổi (Postgres vẫn chọn Seq Scan vì dataset nhỏ) — đây là kết quả HỢP LỆ, không phải làm sai; ghi lại lý do (dataset nhỏ, Seq Scan rẻ hơn).
   - ⚠️ Lỗi thường gặp: kỳ vọng index luôn làm nhanh hơn — với mart dataset học tập (nhỏ), planner có thể bỏ qua index vì Seq Scan vẫn rẻ hơn; đừng cố ép dùng index bằng cách khác (vd `SET enable_seqscan = off`) trừ khi mục đích là học cách planner quyết định.
