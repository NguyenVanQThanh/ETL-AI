## 3. Kiến thức quan trọng / Keyword cần nắm

Danh sách khái niệm PHẢI hiểu được (không chỉ copy-paste code) trước khi coi buổi này là xong:

- **SCD Type 1 vs SCD Type 2** — SCD1 (đã làm ở P1.S3): mỗi khi seller đổi thông tin, `UPDATE` đè trực tiếp lên row cũ → mất lịch sử, chỉ biết trạng thái hiện tại. SCD2: mỗi lần thay đổi tạo THÊM 1 row mới, row cũ được "đóng" lại (đánh dấu hết hiệu lực) → giữ được toàn bộ lịch sử thay đổi theo thời gian, query được "seller này lúc thời điểm X trông như thế nào".
- **dbt snapshot** — feature built-in của dbt-core, tự động hoá việc implement SCD Type 2 mà không cần tự viết logic `MERGE`/`INSERT ... WHERE changed` tay. Định nghĩa 1 lần trong file `snapshots/*.sql`, mỗi lần chạy `dbt snapshot` dbt tự so sánh source với snapshot table hiện tại và tự quyết định insert row mới hay giữ nguyên.
- **Snapshot strategy: `timestamp` vs `check`** — `timestamp`: dựa vào 1 cột `updated_at` (hoặc tương đương) trong source, dbt so sánh giá trị mới > giá trị đã lưu để biết có thay đổi. `check`: không cần cột timestamp, dbt so sánh giá trị của danh sách cột chỉ định (`check_cols`) giữa lần chạy hiện tại và snapshot — cột nào đổi thì coi là có thay đổi. Olist source không có `updated_at` thật (data tĩnh) nên buổi này cân nhắc dùng `check` strategy, hoặc giả lập cột `updated_at` để dùng `timestamp` (xem step 1).
- **`dbt_valid_from` / `dbt_valid_to` / `dbt_scd_id`** — 3 cột metadata dbt TỰ SINH ra trong snapshot table, không cần tự thêm tay: `dbt_valid_from` = thời điểm row này bắt đầu có hiệu lực, `dbt_valid_to` = thời điểm row này hết hiệu lực (NULL nếu đang là version hiện tại), `dbt_scd_id` = hash key duy nhất cho từng version của 1 record. Đây là điểm khác biệt lớn nhất so với tự build SCD2 tay: dbt tự quản lý toàn bộ 3 cột này, mình không cần viết logic tính `valid_from`/`valid_to`.
- **`is_current` flag** — không phải cột dbt tự sinh, mà là cột mình tự derive thêm ở model đọc từ snapshot: `is_current = (dbt_valid_to IS NULL)`. Roadmap gốc yêu cầu `valid_from`, `valid_to`, `is_current` trên `dim_seller` — thực chất `valid_from`/`valid_to` map trực tiếp từ `dbt_valid_from`/`dbt_valid_to`, còn `is_current` là cột tính thêm.
- **Tự build SCD2 tay vs dbt snapshot** — tự build tay nghĩa là viết SQL `MERGE`/logic so sánh, tự tính `valid_from`/`valid_to`, dễ sai edge case (concurrent update, hard delete). dbt snapshot đã đóng gói sẵn logic này, được test kỹ trong ecosystem dbt — ưu tiên dùng built-in trước khi nghĩ tới tự viết tay.

## 4. Các bước nhỏ (step-by-step)

1. **Xác định strategy phù hợp với data Olist**
   - Olist dataset là dữ liệu lịch sử tĩnh (export 1 lần), bảng `sellers` không có cột `updated_at` thật → không thể dùng `timestamp` strategy đúng nghĩa ngay từ đầu.
   - Chọn 1 trong 2 hướng: (a) dùng `strategy: check` với `check_cols` = danh sách cột quan tâm (`seller_city`, `seller_state`, `seller_zip_code_prefix`) — không cần `updated_at`; hoặc (b) thêm cột `updated_at` giả lập (`DEFAULT now()`) vào raw table để dùng `strategy: timestamp` cho gần với thực tế production hơn.
   - Khuyến nghị buổi này: dùng **`check` strategy** trước (đơn giản, đúng bản chất data tĩnh), có thể note lại `timestamp` strategy là cách làm chuẩn khi có `updated_at` thật ở production.
   - Kỳ vọng thấy gì: quyết định rõ strategy nào dùng, ghi lý do vào Nhật ký.

2. **Viết config snapshot `snapshots/dim_seller_snapshot.sql`**
   - Tạo file trong dir `snapshots/` của dbt project (tạo dir nếu chưa có).
   - Config mẫu (strategy `check`):
     ```sql
     {% snapshot dim_seller_snapshot %}

     {{
         config(
           target_schema='snapshots',
           unique_key='seller_id',
           strategy='check',
           check_cols=['seller_city', 'seller_state', 'seller_zip_code_prefix'],
         )
     }}

     select
         seller_id,
         seller_zip_code_prefix,
         seller_city,
         seller_state
     from {{ source('olist_raw', 'sellers') }}

     {% endsnapshot %}
     ```
   - Nếu chọn hướng `timestamp` thay vào đó: thêm `strategy='timestamp'`, `updated_at='updated_at'`, bỏ `check_cols`.
   - Kỳ vọng thấy gì: file compile được, không lỗi Jinja syntax khi `dbt parse`.

3. **Chạy `dbt snapshot` lần đầu**
   - Lệnh: `dbt snapshot --select dim_seller_snapshot`.
   - Kỳ vọng thấy gì: table `dim_seller_snapshot` xuất hiện trong schema `snapshots` (Postgres), có đủ cột source + `dbt_valid_from`, `dbt_valid_to` (đang NULL cho toàn bộ row vì là lần chạy đầu), `dbt_scd_id`.
   - ⚠️ Lỗi thường gặp: quên tạo `source()` cho `sellers` trong `sources.yml` → dbt báo "source not found". Kiểm tra `sources.yml` đã declare đúng schema/table trước khi chạy.

4. **Build model `dim_seller` mới đọc từ snapshot, thêm `is_current`**
   - Sửa (hoặc tạo mới) model `models/marts/dim_seller.sql` để `ref()` tới `dim_seller_snapshot` thay vì raw table:
     ```sql
     select
         seller_id,
         seller_city,
         seller_state,
         seller_zip_code_prefix,
         dbt_valid_from as valid_from,
         dbt_valid_to as valid_to,
         (dbt_valid_to is null) as is_current
     from {{ ref('dim_seller_snapshot') }}
     ```
   - Chạy `dbt run --select dim_seller`.
   - Kỳ vọng thấy gì: `dim_seller` có đủ cột `valid_from`, `valid_to`, `is_current` như checklist roadmap yêu cầu; mỗi seller hiện đúng 1 row với `is_current = true`, `valid_to = NULL`.

5. **Giả lập seller đổi thông tin để test SCD2**
   - Vì data Olist tĩnh, cần tự tạo thay đổi giả để kiểm tra: chọn 1 `seller_id` cụ thể, `UPDATE` trực tiếp vào raw table `sellers` (đổi `seller_city` sang giá trị khác) qua `psql` hoặc script SQL.
     ```sql
     update raw.sellers
     set seller_city = 'sao_paulo_test_update'
     where seller_id = '<chọn 1 seller_id có thật>';
     ```
   - Chạy lại `dbt snapshot --select dim_seller_snapshot` rồi `dbt run --select dim_seller`.
   - Kỳ vọng thấy gì: `dim_seller_snapshot` giờ có 2 row cho `seller_id` đó — row cũ có `dbt_valid_to` = timestamp lúc chạy snapshot lần 2 (không NULL nữa), row mới có `dbt_valid_from` = cùng timestamp đó và `dbt_valid_to` = NULL.
   - ⚠️ Lỗi thường gặp: quên chạy lại `dbt snapshot` trước khi query — model `dim_seller` chỉ phản ánh đúng khi snapshot table đã được update.

6. **Viết query kiểm tra lịch sử thay đổi**
   - Query xem toàn bộ lịch sử của 1 seller:
     ```sql
     select seller_id, seller_city, valid_from, valid_to, is_current
     from dim_seller
     where seller_id = '<seller_id đã update ở step 5>'
     order by valid_from;
     ```
   - Kỳ vọng thấy gì: đúng 2 row — row cũ (`is_current = false`, có `valid_to`), row mới (`is_current = true`, `valid_to` NULL) — đúng theo yêu cầu roadmap "query lịch sử thay đổi seller theo thời gian đúng".
