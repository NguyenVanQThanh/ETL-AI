## 1. Prerequisite — Chuẩn bị những gì

- [ ] Buổi trước (`P1.S01`) đã xong: Postgres có data thật trong schema `raw` (các bảng Olist: orders, customers, order_items, products, sellers, reviews...), `docker compose up` chạy được và container Postgres đang sống.
- [ ] Python 3 + virtualenv/venv đã có sẵn trên máy; đã `pip install dbt-core dbt-postgres` (adapter `dbt-postgres` tự kéo theo `dbt-core` tương thích).
- [ ] Credential kết nối Postgres đã có: host, port, user, password, dbname — lấy từ file `.env`/`docker-compose.yml` của project, KHÔNG hardcode giá trị thật vào file này hay vào `dbt_project.yml`. `profiles.yml` (nơi chứa credential) đặt ngoài git — dùng env var (`env_var('DBT_PG_PASSWORD')` trong `profiles.yml`) nếu muốn tránh plaintext.
- [ ] Đã biết khái niệm cơ bản: SQL SELECT/CAST/alias, YAML syntax, khái niệm schema trong Postgres.

| Tech | Vai trò trong buổi này | Version/note |

## 3. Kiến thức quan trọng / Keyword cần nắm

Danh sách khái niệm PHẢI hiểu được (không chỉ copy-paste code) trước khi coi buổi này là xong:

- **`source()` vs `ref()`** — `source()` trỏ tới bảng raw (khai báo trong `sources.yml`), CHỈ được dùng trong staging models. `ref()` trỏ tới model dbt khác (staging/intermediate/mart), dùng ở mọi layer sau staging. Model không thuộc `staging` không được gọi `source()` trực tiếp — luôn qua `ref()` một model staging.
- **Staging layer philosophy** — 1 staging model = 1 source table (quan hệ 1:1), KHÔNG join, KHÔNG business logic, KHÔNG aggregate. Transform tối thiểu: rename cột cho rõ nghĩa, cast type đúng, có thể split/combine field đơn giản (vd tách timestamp). Mọi logic phức tạp hơn đẩy xuống layer intermediate/marts (buổi sau).
- **dbt DAG/lineage** — dbt tự build dependency graph từ `ref()`/`source()` trong code, quyết định thứ tự build model (`dbt run` build theo topological order, không cần khai báo thứ tự tay). Xem bằng `dbt docs generate` + `dbt docs serve`.
- **Materialization = view cho staging** — staging models mặc định `materialized: view` (nhẹ, luôn phản ánh data mới nhất từ raw, không tốn storage) — khác với marts thường `table`/`incremental` (buổi sau). Set trong `dbt_project.yml` hoặc config block đầu file `.sql`.

## 4. Các bước nhỏ (step-by-step)

1. **`dbt init`**
   - Trong thư mục project (hoặc thư mục riêng `dbt/` nếu muốn tách khỏi code ingest), chạy `dbt init olist_dw` (tên project tuỳ chọn). dbt hỏi chọn adapter → chọn `postgres`.
   - Kỳ vọng: thư mục `olist_dw/` được tạo với `dbt_project.yml`, `models/`, và dbt tự tạo/append entry vào `~/.dbt/profiles.yml`.
   - ⚠️ Lỗi thường gặp: `dbt init` tạo `profiles.yml` ở `~/.dbt/` (home directory) theo mặc định, KHÔNG phải trong project — dễ quên vị trí. Có thể override bằng flag `--profiles-dir <path>` nếu muốn giữ profile trong repo (nhưng khi đó phải tự đảm bảo file này không bị commit nếu chứa credential thật).

2. **Cấu hình `profiles.yml` trỏ Postgres**
   - Mở `~/.dbt/profiles.yml`, điền đúng tên profile khớp `profile:` trong `dbt_project.yml`:
     ```yaml
     olist_dw:
       target: dev
       outputs:
         dev:
           type: postgres
           host: localhost
           user: "{{ env_var('DBT_PG_USER') }}"
           password: "{{ env_var('DBT_PG_PASSWORD') }}"
           port: 5432
           dbname: olist
           schema: staging
           threads: 4
     ```
   - `schema: staging` — đây là schema đích dbt sẽ tạo ra các model `stg_*` (tách biệt với `raw`).
   - Verify: `dbt debug` từ trong thư mục `olist_dw/` → phải báo `All checks passed!`.
   - ⚠️ Lỗi thường gặp: quên set env var `DBT_PG_USER`/`DBT_PG_PASSWORD` trước khi chạy → `dbt debug` fail connection. Set trong shell hoặc `.env` rồi `source`.

3. **Khai báo `sources.yml` cho schema `raw`**
   - Tạo `models/staging/olist/_olist__sources.yml`:
     ```yaml
     version: 2
     sources:
       - name: olist_raw
         schema: raw
         tables:
           - name: orders
           - name: customers
           - name: order_items
           - name: products
           - name: sellers
           - name: reviews
     ```
   - Kỳ vọng: `dbt source freshness` hoặc `dbt ls --resource-type source` list đủ 6 source table, không lỗi "table not found".

4. **Viết từng model `stg_*.sql`** — mỗi file 1:1 với 1 source table, transform tối thiểu (rename cột snake_case rõ nghĩa, cast type đúng, KHÔNG join/aggregate):
   - `models/staging/olist/stg_orders.sql`:
     ```sql
     select
         order_id,
         customer_id,
         order_status,
         cast(order_purchase_timestamp as timestamp) as purchased_at,
         cast(order_delivered_customer_date as timestamp) as delivered_at
     from {{ source('olist_raw', 'orders') }}
     ```
   - `models/staging/olist/stg_customers.sql` — rename `customer_zip_code_prefix` → `zip_code_prefix`, cast id về text nếu cần.
   - `models/staging/olist/stg_order_items.sql` — cast `price`, `freight_value` về `numeric`.
   - `models/staging/olist/stg_products.sql` — cast các cột `product_*_cm`/`_g` về `numeric`.
   - `models/staging/olist/stg_sellers.sql` — tương tự customers (zip code, city, state).
   - `models/staging/olist/stg_reviews.sql` — cast `review_score` về `int`, `review_creation_date`/`review_answer_timestamp` về `timestamp`.
   - Tất cả dùng `{{ source('olist_raw', '<table>') }}`, KHÔNG dùng tên schema/table cứng.
   - Thêm block config materialization (nếu chưa set default trong `dbt_project.yml`):
     ```sql
     {{ config(materialized='view') }}
     ```
   - ⚠️ Lỗi thường gặp: quên cast type → `dbt run` chạy được nhưng model sau (marts) join sai kiểu dữ liệu (vd text vs numeric) lỗi ở buổi sau. Cast ngay từ staging.

5. **`dbt run`**
   - Chạy `dbt run` từ thư mục `olist_dw/`. dbt tự resolve DAG từ `source()` trong 6 file trên, build view trong schema `staging`.
   - Kỳ vọng: output toàn bộ `OK created sql view model staging.stg_*` — không có dòng `ERROR`/`FAIL`.

6. **`dbt docs generate` (chạy thử)**
   - Chạy `dbt docs generate` rồi `dbt docs serve` để xem lineage graph — chỉ để verify DAG đúng (source → stg_*), không phải deliverable chính buổi này.
   - Kỳ vọng: trang docs mở được, lineage graph hiển thị 6 node source `olist_raw.*` nối tới 6 node `stg_*` tương ứng, không có edge sai.

## 5. Output mong muốn

- [ ] `dbt run` PASS 100% — toàn bộ 6 model `stg_orders`, `stg_customers`, `stg_order_items`, `stg_products`, `stg_sellers`, `stg_reviews` build thành công (view) trong schema `staging`, không có model nào `ERROR`/`SKIP`.
- [ ] File tạo ra: `olist_dw/models/staging/olist/_olist__sources.yml` + 6 file `stg_*.sql` cùng thư mục.
- [ ] Cách tự kiểm tra:
  - `dbt run` → check log không có `Completed with N error(s)`.
  - `dbt ls --select staging.*` → list đủ 6 model.
  - Query trực tiếp: `psql -c "select * from staging.stg_orders limit 5;"` (hoặc tool GUI) → thấy data thật, cột đã rename/cast đúng kiểu (dùng `\d staging.stg_orders` để check type).
